Why a Static Page Is Missing from Search: An Indexability Decision Tree

Diagnose deployment, HTTP status, robots rules, noindex, canonical URLs and sitemap eligibility in the right order, with a practical evidence log.

Scope: A diagnostic worksheet for static educational websites, not a guarantee of search indexing. All examples are hypothetical; no purchases or subscriptions are required.

Start with the page a visitor actually receives

A file in GitHub is not necessarily a live web page. Open the exact intended HTTPS address in a private browser window and record its final URL, response status, visible title and whether the content is the version you expect. If it redirects, inspect the destination rather than assuming the original URL is the canonical page. A GitHub Actions success message proves only the action's reported steps, not that a separate host deployed the output. If the browser shows a different website, stop: deployment mapping is a prerequisite to every later indexing step.

Step 1: Does the exact URL serve the intended document?

An HTTP 200 response with the wrong page is not a pass. An HTTP 404 means the requested path was not found; check the hosting output directory, filename capitalization, trailing slash rules and build artifact. A 403 or timeout is not interchangeable with a 404. Test a browser request as well as a command-line request where appropriate, because bot protections and hosting differences can affect results. If the hostname itself fails DNS resolution, investigate the DNS record and hosting domain assignment; do not edit canonical tags to compensate for an unreachable domain.

Step 2: Is crawling allowed, and is indexing separately allowed?

Robots.txt controls crawling requests for compliant crawlers; a robots disallow directive is not a reliable way to remove a URL from search results. A robots meta tag such as noindex,follow or an X-Robots-Tag header can request exclusion from indexing, but a crawler must be able to fetch the page to see the directive. Inspect the response headers and the actual HTML head, not just source files. A site can have robots.txt Allow: / and still contain noindex pages. Do not remove noindex from a staging guide until the correct production URL is live and ready for discovery.

Step 3: Is the canonical address consistent?

The canonical link is a signal indicating the preferred URL among duplicates, not a guarantee that a search engine will select it. Compare the address bar, redirect target, canonical href, internal links and sitemap entry. They should point to the same preferred HTTPS page when that is the publisher's intention. A canonical pointing to a different domain may be appropriate for genuinely duplicated syndicated content, but it should not be copied blindly across unrelated sites. If a production hostname serves someone else's site or a different deployment, do not force a repository's URLs into that hostname's sitemap.

Step 4: Does the sitemap describe reality?

A sitemap is a discovery hint, not an indexing command. Include only canonical, publicly reachable, intended-to-be-indexed URLs from the actual deployment. Exclude 404s, redirecting aliases, private archives, staging articles and pages with noindex. Use lastmod only when the page's substantive content genuinely changed; don't stamp every URL with today's date after editing a navigation menu. Check that sitemap.xml is well-formed XML and that robots.txt references the correct public sitemap. A valid XML file containing unverified paths is still a misleading inventory.

Step 5: Check Search Console evidence without overinterpreting it

For a property you control, confirm the correct property scope and ownership verification before interpreting coverage. URL Inspection can show the indexed or crawled state Google has recorded, but its result may lag behind a new deployment. A sitemap submission confirms receipt, not guaranteed crawling or indexing. Record the inspected URL, inspection date, reported canonical and any exclusion reason. Never use a verification token belonging to a different property; verification is property-specific. If the integration lacks authorized writing access, record submission as pending instead of implying it happened.

Worked example: source exists, production returns 404

Imagine an editor commits /guide-a.html to a repository and adds a canonical URL on example.test. The build copies the file to a public folder, but the configured hosting site still serves an older project. Visiting /guide-a.html returns 404. The correct diagnosis is not “Google is slow”: the public page is missing. The safe sequence is to confirm the hosting project and output path with the owner, deploy without overwriting unrelated content, verify HTTP 200 and intended HTML, check noindex and canonical, and only then add the URL to the production sitemap. No Search Console submission can repair a missing deployed page.

A copyable investigation log

For each URL, record: intended URL; tested date; DNS outcome; HTTP status; redirect target; visible page identity; robots.txt rule; robots meta or header; canonical href; internal navigation link; sitemap inclusion; Search Console observation; evidence link or screenshot; next action; owner. Mark every field “not checked” until verified. Prioritize fixes by the earliest failed gate. If the page is reachable but not indexed, do not conclude there is a penalty: eligibility and selection are different from guaranteed inclusion.

Decision and maintenance rules

If DNS or deployment fails, stop and resolve hosting. If HTTP status or visible content is wrong, repair the page before touching indexing controls. If noindex is intentional, preserve it and exclude the page from sitemaps. If canonical and internal links conflict, correct the publisher's preferred destination. If everything is technically eligible, improve usefulness and check Search Console rather than repeatedly resubmitting. After a substantive content change, update only that page's lastmod if it is actually in the verified live sitemap. Avoid mass re-dating, artificial traffic and claims that any checklist guarantees search placement.
